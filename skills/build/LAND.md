# Land the spec

A repository's milestones **land** when its spec branch reaches its base, as one commit per milestone, with no merge commit. A spec in one repository lands once, after its last milestone. A spec across several lands its repositories each time the build moves on to a wave in another repository, so each repository's base takes the milestones in the order [CONTRACT-CHANGE.md](../to-tickets/CONTRACT-CHANGE.md) cut them, and every base keeps working with the others.

## Land repositories

The repositories are those holding **unlanded** milestones (squashed, with a **Landed** line that names no commit), by the build's step 1. Work in each by [FORMAT.md](../brain/FORMAT.md)'s working repository rules, and find its base branch by the build's **Branches**.

1. **Check what has landed.** For each repository, when `git -C <root> merge-base --is-ancestor sdd/<spec-folder>/spec <base>` succeeds, its milestones are already on the base: take it straight to step 3. Done when you know which repositories still have to land.

2. **Ready each one.** For each repository still to land: when the root is not open, ask the user to run `/add-dir <root>`, and stop. When `git -C <root> status --porcelain` is not empty, report it and stop. Note its base's commit (`git -C <root> rev-parse <base>`), then run `git -C <root> rebase <base> sdd/<spec-folder>/spec`; on a conflict, run `git -C <root> rebase --abort`, report the conflicting files, tell the user that once they rebase `sdd/<spec-folder>/spec` onto `<base>` themselves, running the same `/build` again lands it, and stop. Run the repository's full suite on the rebased branch, from its root. When it fails, the base's new commits broke the spec: dispatch a fixer by the build's step 8 brief, with the Context block (**Branch** `sdd/<spec-folder>/spec`), the paths of the repository's last unlanded `milestone.md` and `spec.md`, and the failing command and the end of its output, then run the suite again; after two failed fixes, write `failed` into the **Phase** line of the repository's last unlanded milestone, report the failure and stop, leaving its base untouched. Done when every repository still to land is rebased with its suite passing.

3. **Land them.** Ask the user once before changing any base, naming each repository, the milestones that land in it, and that its suite passes. On a yes, in each repository check out the base and run `git -C <root> merge --ff-only sdd/<spec-folder>/spec`. Then record each landed milestone: `git -C <root> log --reverse --format=%H <noted base commit>..<base>` lists the repository's new commits in milestone order, one per unlanded milestone; set each milestone's **Landed** line to its own commit, replacing its `none`, and write `landed` into its **Phase** line. When the user declines, the build stops: later milestones build on these being on their bases. Done when each unlanded milestone's **Landed** names its commit, or the user declined.

## When no milestone is open

1. **Land the rest**, by **Land repositories**. Done when every milestone's **Landed** names a commit, or the user declined.

2. **Record the spec's landing.** Write `**Landed:** <slug>@<SHA>, …` into `spec.md`, under its **Base** line, with one entry per repository in **Repos**: the **Landed** SHA of its last milestone. Specs that depend on this one wait for that line. Skip this while any milestone is open or unlanded, or when `spec.md` already has its **Landed** line. Done when `spec.md` holds the **Landed** line, or a milestone has not landed.

3. **Clean up and hand over.** In each repository, offer to delete the spec's branches (`git -C <root> branch -D` on each of `git -C <root> branch --list 'sdd/<spec-folder>/*'`); delete them when the user agrees. Report every milestone, from its files: its repository, the tickets built with their **Commit** lines, what its `review.md` fixed, and its **Squash** and **Landed** commits. Then report one **Decided for you** section listing each escalated finding across the milestones' `review.md` files with its milestone and Answer, the commits now on each base, and that the spec is built. When any repository in **Repos** has a remote, add the hint `/pr <spec-id>` to open its PRs, one per landing. For each repository whose card has an `explored` line, add the hint `/brain explore <slug>` once its base is pushed, so its explored notes catch up with the change. Done when the user has the report.

4. **Keep what was learned.** The tickets' Notes and the review answers live in the brain's `.sdd/`, on this machine only, so whatever they hold that a later change needs is lost with it. Dispatch one `alper-brain:scout`, its brief opening with the Context block by [BRIEF.md](../brain/BRIEF.md) (**Works in** the brain, **Also reads** each repository in **Repos**, **Spec** the spec folder, never a ticket's path, **Writes** nothing), with this brief: "Gather the gotchas from the tickets' Notes, the escalated Answers in the milestones' `review.md` whose reasons a later change would need, and the spec's Design Patterns rows that `design-patterns`' **Recording** says outlive the spec. For each, find whether the code on its repository's base, an ADR, or a note under the brain's `repos/<slug>/` or `shared/` already states it, and report it as **stated**, with the file, or **new**, with the repository it bears on." The spec does not survive, so it is no reason to drop a candidate. Invoke the `brain` skill to record the **new** ones as one list of candidates, each in the notes of the repository it bears on. For a spec of one milestone with few Notes, sift them inline instead. Done when the user has picked from the list, or nothing was left to offer.

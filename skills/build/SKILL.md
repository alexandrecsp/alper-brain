Build a spec one **wave** of milestones at a time, from the files `to-tickets` wrote under the active brain's `.sdd/specs/NNN-<slug>/`. Each **milestone** builds in its **repository**, the one its **Repo** line names, worked in by [FORMAT.md](../brain/FORMAT.md)'s working repository rules: its root comes from the brain's `.sdd/links.json`, every git command runs as `git -C <root>`, and every suite runs from the root. Each ticket is built by a **builder sub-agent** in a fresh context, the milestone closes with one `review-changes` over its whole diff, and it is squashed from its own branch into the spec's branch in that repository as one commit. A repository's milestones land on its base each time the build moves on to a wave in another repository, and once the last milestone is in (see [LAND.md](LAND.md)). Everything stays local: never push, fetch or open a PR; the user pushes by hand.

By default one call builds the whole spec: step 10 returns to step 1 for the next wave, and once no milestone is open, step 1 lands the spec by [LAND.md](LAND.md). Given a **milestone id** (the milestone folder's number, with or without an `m`, such as `m01`, `M001` or `1`, or its folder name), the call runs in **milestone mode**: it builds that one milestone and hands over at step 10. The milestone id comes after the spec id, or alone when it starts with `m`, for the spec in this conversation. A call stops early only where a step says to stop, and running the same call again resumes it.

Dispatch every builder sub-agent as the `alper-brain:builder` agent. A **fixer** is the `alper-brain:fixer` agent: it takes the review's findings and a failing check. The review's escalated findings go to the `alper-brain:arbiter` agent, which decides them in place of the user. Open every brief with the Context block by [BRIEF.md](../brain/BRIEF.md): **Works in** the milestone's repository, **Spec** the ticket or `milestone.md`, **Branch** the milestone's branch, **Notes** the spec's **Brain notes** line, and **Writes** the files under the root plus, for a builder, its ticket file. Talk to sub-agents through **context pointers**: the paths of the ticket, its `milestone.md` and the `spec.md`, rather than their contents. After each builder or fixer reports, check where it wrote by BRIEF.md's **After a sub-agent that changes a repository reports**; when a check fails, treat it as a sub-agent that could not finish its work. List every **Needs the user** item a sub-agent reports in the hand-over's **Decided for you** section.

## Branches

In each repository, the spec's branch is `sdd/<spec-folder>/spec` and each of its milestones' is `sdd/<spec-folder>/M<NNN>`, with `NNN` the milestone folder's number, such as `sdd/003-invoice-export/spec` and `sdd/003-invoice-export/M001`: the `sdd/<spec-folder>/` prefix groups a spec's branches, so they are listed and cleaned up with one glob. A repository's **base branch** is its `<slug>@<branch>` entry in the **Base** line of `spec.md`; When it has none, take its remote's default (`git -C <root> symbolic-ref --short refs/remotes/origin/HEAD`, without `origin/`); when that fails, ask the user. Then add the entry to the **Base** line, creating it under the **Key** line, so every landing and every spec that depends on this one reads the same base.

## Waves

A milestone **waits on** another when it builds in the same repository and is numbered after it, or when one of its tickets' **Depends on** names a ticket in it, directly or through the tickets those name. The **wave** is every open milestone that waits on no other open milestone: milestones in different repositories with nothing between them build side by side, since each has its own working tree, while a spec in one repository has a wave of one milestone at a time. Within a wave the builders run in rounds (step 4), one ticket per milestone, all in one message; then steps 5 to 9 close each milestone in turn, lowest-numbered first, since the review's sub-agents run from this session.

## Phase

Once its tickets are `done`, a milestone is still closing: reviewed, decided, fixed, checked, squashed. Steps 5 to 9 each begin by writing their word into `milestone.md`'s **Phase** line, above **Squash**: `review`, `decide`, `fix`, `check`, `squash`. Step 8 writes `failed` when it gives up on a failing check: the brain page shows it as waiting on the user. Once squashed, LAND.md writes `landed` when the milestone lands, or `failed` when its landing gives up.

A build that stopped **resumes** each milestone of the wave step 1 picks from its own Phase line: `none` at step 4, `review` at step 5, `decide`, or the `ask` that older builds left, at step 6, `fix` at step 7, `check` or `failed` at step 8, `squash` at step 9. Steps 1 to 3 run on every milestone.

## Process

1. **Pick the wave.** Find the spec folder from the spec id by [SPEC-ID.md](../to-spec/SPEC-ID.md), or, without one, take the spec folder from this conversation. When `spec.md` has an **Abandoned** line, report it and stop. A milestone is **open** until its **Squash** names a commit, and **unlanded** from then until its **Landed** names one. When no milestone is open, follow [LAND.md](LAND.md)'s **When no milestone is open** instead. Take the wave by **Waves**. In milestone mode, the wave is the named milestone alone: take the folder under `milestones/` whose name starts with the milestone id's number padded to three digits; when none matches, or it is not open, report that and stop; when it waits on an open milestone, report that that one comes first and stop. When the wave holds a milestone whose **Repo** differs from the **Repo** of an unlanded milestone, the build is moving on: land every repository holding unlanded milestones first, by LAND.md's **Land repositories**, and stop when it stops. Once per call, check every repository the call will change: in milestone mode, the wave's repository and those it lands first; otherwise the **Repo** of every open or unlanded milestone. Ask the user, in one message, to run `/brain link` for any missing from `.sdd/links.json` and `/add-dir <root>` for any not open, and stop until they are; name any whose `git -C <root> status --porcelain` is not empty, since step 3 stops on it. Done when you can name the wave's milestones, each with its repository and the step its Phase resumes at, and every repository the call changes is linked and open.

2. **Check the dependencies.** Skip this unless the wave holds the spec's first milestone and none of its tickets has left `todo`: otherwise an earlier pass already ran it. For each spec named in the **Depends on** line of `spec.md`, which is absent or `None` when there are none: when its folder is missing under `.sdd/specs/`, report it and stop; when its `spec.md` has an **Abandoned** line, report that this spec must be revised to drop it, and stop; when a repository its **Landed** line names is missing from `.sdd/links.json`, ask the user to run `/brain link`, and stop; when its `spec.md` has no **Landed** line, or for any of its `<slug>@<SHA>` entries `git -C <that repository's root> merge-base --is-ancestor <SHA> <its base>` fails, report that this spec waits on it and stop. Then dispatch one `alper-brain:spec-reviewer` agent per dependency, in parallel, with the Context block (the repositories the dependency's **Landed** line names under **Works in** and **Also reads**, read only, and **Writes** nothing), the paths of both `spec.md` files, and this brief:

   > Check whether the dependency was built as this spec assumes. For each bullet of this spec's **Relies On** section that names the dependency, read the code it touches as it stands on the branch the dependency's **Base** line names for that repository, with `git -C <root> show <base>:<path>` (the working tree may hold another branch), and the Notes of the dependency's tickets, and report the bullet as **holds** or **drifted**, with what the code does instead. Change nothing.

   When any bullet drifted, show the user the report and stop: revising the spec is the user's call. Done when every dependency has landed and every Relies On bullet holds, or the spec has none.

3. **Prepare the branches**, for each milestone of the wave in its own repository. Find the repository's root in the brain's `.sdd/links.json`; when it is missing, ask the user to run `/brain link`, and stop. When the root is not open, ask the user to run `/add-dir <root>`, and stop. When `git -C <root> status --porcelain` is not empty, report it and stop: the commits must hold only this milestone's work. Find the base branch by **Branches**. When the spec's branch does not exist in the repository, create it from the base. When the milestone's branch exists, check it out; otherwise create it from the spec's branch. The **fixed point**, the commit the review diffs against, is `git -C <root> merge-base sdd/<spec-folder>/spec HEAD`, which survives rebases. Done when each milestone's branch is checked out and its fixed point resolves.

4. **Build the tickets**, in rounds. A milestone's tickets build in number order, each only on the tickets before it. Each round takes, from every milestone of the wave with a ticket not `done`, its lowest-numbered such ticket: set each one's **Status** to `doing`, then dispatch one builder sub-agent per ticket, all in one message and in the foreground, each with its own milestone's Context block, the paths of the ticket, `milestone.md` and `spec.md`, the slug and root (from `.sdd/links.json`) of the **Repo** of each other milestone holding a ticket its **Depends on** names, under **Also reads**, and this brief:

   > Build this ticket in the repository the Context block names. First read the earlier tickets in its milestone folder and the tickets its **Depends on** names, their Notes, the commits their **Commit** lines name, each with `git -C` the root of the repository its milestone built in, and the notes the Context block lists. Invoke the `tdd` skill, testing at the seams the ticket's acceptance criteria name. Place and name every new file by `<root>/docs/STRUCTURE.md`, invoking the `project-structure` skill where it is silent. Build its Design patterns rows at their Where. Leave the full suite to the milestone check: you are done building when each acceptance criterion has a test at its seam that you saw fail, then pass, and the unit suite and your e2e tests pass. Then fill the ticket's Notes with what its diff can't show the next ticket (decisions the ticket left open, departures from it, gotchas you hit) in a few bullets, or "None". Commit everything by invoking the `commit` skill with the spec folder and the repository. Then write the commit's SHA into the ticket's **Commit** line and set its **Status** to `done`. Report the commit, and anything you could not build.

   When the ticket was already `doing` or `blocked`, an earlier build stopped on it: add to the brief that part of its work may already be committed on this branch, and that its Notes say what blocked it. When a builder could not build its ticket, dispatch a fixer once with the same brief, adding the builder's report and that part of its work may already be committed. When the fixer could not build it either, set its **Status** to `blocked`, write what stopped it into its Notes, and once the round's other builders have reported, report it to the user and stop: the tickets after it may depend on it. Start the next round once every builder of this one has reported and passed its check. Done when every ticket in the wave is `done` and committed.

   Steps 5 to 9 close one milestone: run them for each milestone of the wave in turn, lowest-numbered first.

5. **Review.** When the milestone folder holds a `review.md` whose **Head** is the branch's `HEAD`, the milestone as it stands is already reviewed: take that report. Otherwise invoke the `review-changes` skill with the fixed point, the milestone folder and the repository; it saves its report as the milestone's `review.md`. Show the user the report. Done when the milestone's `review.md` has the branch's `HEAD` as its **Head**.

6. **Decide.** When `review.md` has no finding flagged **escalate** without an **Answer** line, skip this. Otherwise dispatch one arbiter with the Context block (**Notes** adding the `contract` notes in the brain's `shared/` whose `repos` name this milestone's **Repo**, **Also reads** the root of each other repository those notes name, and **Writes** nothing), the paths of `review.md`, `milestone.md` and `spec.md`, and this brief:

   > Decide each finding in this review flagged escalate that has no **Answer** line. For each, read its hunk in the repository the Context block names, the rule or requirement it cites, the ADRs and `decision` notes it touches and the code that calls what it would change. Take each consumer's call sites from the review's Consumers section, reading the repositories the contract notes name only where a finding needs more. Answer it with one of: fix it as proposed; fix it another way, saying how; or skip it. Give a one-line reason, and when your answer builds something other than what the spec or a ticket says, name those tickets. Weigh the findings together: they come from one diff. When an answer changes an interface another repository calls, keep the old shape offered beside the new one, unless a later milestone of this spec migrates that consumer: name the milestone. Report one line per finding, by its ID. Change nothing.

   Write each answer under its finding as `**Answer:** <answer> — <reason>`. For each ticket an answer names, add a bullet to its Notes: `Departs from the spec: <what is built instead>, by review finding <the finding in a few words>`. Notes override `spec.md` for every later reader, so `spec.md` stays as the user approved it. Done when every escalated finding has its Answer.

7. **Fix.** When `review.md` holds nothing to fix, skip this. Otherwise dispatch one fixer with the Context block, the path of `review.md`, and this brief:

   > Fix the findings in this review, in the repository the Context block names: every one not flagged escalate, and each escalated one as its answer says, skipping any with a **Fixed** or **Not fixed** line. Prove each fix with the smallest test at the seam it touches; a refactor needs only the suite. Finish with the unit suite and your e2e tests passing. Commit by invoking the `commit` skill with the spec folder and the repository. Report one line per finding, by its ID: fixed, with the commit, or not fixed, with why.

   Write the fixer's line under each finding in `review.md`, as `**Fixed:** <SHA>` or `**Not fixed:** <reason>`. The review runs once per milestone, so fixing never turns into a review loop. Done when every finding to fix has its line, or there was nothing to fix.

8. **Check the increment.** Run the repository's full suite and the check in `milestone.md`'s **Done when**, from its root: this is the milestone's one full run. When either fails, dispatch a fixer with the Context block, the paths of `milestone.md` and `spec.md`, the failing command and the end of its output, and this brief, then run both again:

   > Make this failing check pass in the repository the Context block names. Find the cause before changing anything. Fix the code; change a test, the check or the milestone's **Done when** only when it contradicts the ticket or spec it proves, and say so. Commit by invoking the `commit` skill with the spec folder and the repository. Done when the failing command passes and the unit suite still passes. Report the cause, the commit, and every test you changed.

   After two failed fixes, write `failed` into the **Phase** line, report the failure to the user and stop. Done when both pass.

9. **Squash into the spec.** Check out the spec's branch. When `git -C <root> diff sdd/<spec-folder>/spec sdd/<spec-folder>/M<NNN>` is empty, an earlier build already committed the squash: take `HEAD` as its commit. Otherwise run `git -C <root> merge --squash sdd/<spec-folder>/M<NNN>` and commit it by invoking the `commit` skill with the spec folder and the repository: the subject is the milestone's increment in the present tense, the body one to three bullets. Write the commit's SHA into `milestone.md`'s **Squash** line. Keep the milestone's branch: its ticket commits stay readable there until the spec lands. Done when the squash is committed and recorded.

10. **Hand over.** In milestone mode, report the milestone's repository, the tickets built with their commits, what the review fixed, the squash commit, a **Decided for you** section listing each escalated finding in `review.md` with its Answer, or none, and the next step: `/build <spec-id>` to build the rest and land the spec, or `/build <spec-id> <milestone-id>` with the next milestone's id to build only that one. Otherwise report one line per milestone of the wave (the milestone, its repository, its squash commit and the number of findings fixed) and return to step 1. Done when the user has the report, or outside milestone mode the lines.

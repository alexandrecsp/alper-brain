# Land the spec

A milestone **lands** when its squash reaches its repository's base, as one commit per milestone, with no merge commit. A track lands only once it has no open milestone, so no rebase runs under a milestone being built, and only its **landable** milestones: a milestone is landable once it is squashed, every earlier milestone of its track is landed or landable, and every milestone its **Lands after** or **Builds after** names has landed. Landing in that order gives each base the milestones in the order [CONTRACT-CHANGE.md](../../write-tickets/references/CONTRACT-CHANGE.md) cut them, so every base keeps working with the others. The build's `sdd state`, by its **State**, gives each track's `landable` milestones, and each unlanded one's `onBase`.

Landing rebases a track's spec branch, so each squashed milestone's **Squash** line follows its commit through every rebase: right after one, each milestone's commit is the one in `git -C <root> log --format='%H %(trailers:key=Sdd-Milestone,valueonly,separator=%x2C) %s' <base>..sdd/<spec-folder>/spec` whose `Sdd-Milestone` trailer names it, by the build's step 10. A squash committed before that trailer existed has none: it is the one whose subject is its squash's. A milestone has **landed** once its **Squash** commit is on its base (`git -C <root> merge-base --is-ancestor <Squash SHA> <base>`); a fast-forward keeps the SHA, so its **Landed** commit is that same one.

## Land a track

Work in the track's repository by [FORMAT.md](../../brain/references/FORMAT.md)'s working repository rules. The landing takes the track's landable milestones and lands them without asking.

1. **Land them.** Run `sdd land <spec-folder> --track <slug> --brain <the active brain>`. It records the landable milestones already on the base, from an earlier call that stopped after its merge; rebases `sdd/<spec-folder>/spec` onto the base and writes each squash's rebased commit into its **Squash** line, as the paragraph above finds it; runs the repository's full suite, by its card, at the last landable milestone's **Squash**, the landing's **head**; fast-forwards the base to it; appends the landing to `spec.md`'s **Landings** line in the form FORMAT.md's **Specs** gives it; sets each landed milestone's **Landed** to its **Squash** and its **Phase** to `landed`; and, once every milestone of the spec has landed, writes `spec.md`'s **Landed** line. It prints `landed: <slug> <milestones>`, or `landed: nothing` when the track has none landable. Done when it prints `landed` with no `stopped` line.

2. **When it stops**, it prints `stopped: <why>` and exits 1, with the spec's branch checked out and the base untouched:
   - `dirty`: the repository has uncommitted changes. Report it and stop.
   - `conflict`: it aborted the rebase. Report the conflicting files it names, tell the user that once they rebase `sdd/<spec-folder>/spec` onto `<base>` themselves, running the same `/build` again lands it, and stop.
   - `dropped`: a milestone's squash is gone after the rebase, since the base already held it. Report the milestone and stop: the user checks that the base holds its work, then runs `/build` again.
   - `tip`: the suite failed at the branch's tip, so the base's new commits broke the spec. Dispatch a fixer by the build's step 9, its brief what `sdd dispatch <the last milestone's milestone.md> --agent fixer --branch sdd/<spec-folder>/spec` prints, then the line `Make this failing check pass.` and the failing command and output `land` printed. Then run `sdd verify <the last milestone's milestone.md> --branch sdd/<spec-folder>/spec --commit <each commit it reports> --brain-head <brainHead>`, and, when it prints `ok`, `sdd land` again with `--fold`, which folds the fixer's commits into the last squash, so each milestone stays one commit, and lands. After two failed fixes, write `failed` into the last milestone's **Phase** line, report the failure and stop.
   - `below`: the suite failed below the branch's tip, and `land` wrote `failed` into that milestone's **Phase**. Report the failure and stop: a fix there would have to rewrite the squashes above it, so the user fixes it by hand in that milestone's squash, rebases the squashes above it, then runs `/build` again.

## When no milestone is open

1. **Land the rest.** Until no track that has not stopped has a landable milestone left, land each such track by **Land a track**, in the order of the spec's **Repos** line, skipping a track once it has stopped: one track's landing can make another's landable. Done when every milestone's **Landed** names a commit, or a track stopped.

2. **Record the spec's landing.** `sdd land` writes `**Landed:** <slug>@<SHA>, …` into `spec.md`, under its **Base** line, once every milestone has landed: one entry per repository in **Repos**, the **Landed** SHA of its last milestone. Specs that depend on this one wait for that line. When every milestone has landed and `spec.md` has no **Landed** line, from a call that stopped before it, run `sdd land` for any track: with nothing to land, it writes the line. Done when `spec.md` holds the **Landed** line, or a milestone has not landed.

3. **Keep what was learned.** The tickets' Notes and the review answers live in the brain's `specs/`, on this machine only, so whatever they hold that a later change needs is lost with it. Dispatch one `alper-brain:explorer`, its brief opening with the Context block by [BRIEF.md](../../brain/references/BRIEF.md) (**Works in** the brain, **Also reads** each repository in **Repos**, **Spec** the spec folder, never a ticket's path, **Docs** the absolute path of the `design-patterns` skill's `SKILL.md`, **Writes** nothing), with this brief: "Gather the gotchas from the tickets' Notes, the escalated Answers in the milestones' `review.md` whose reasons a later change would need, and the spec's Design Patterns rows that the **Recording** section of the `design-patterns` SKILL.md under **Docs** says outlive the spec. For each, find whether the code on its repository's base, an ADR, or a brain note whose `repos` names that repository already states it, and report it as **stated**, with the file, or **new**, with the repository it bears on. Change nothing. Done when every ticket's Notes, every escalated Answer and every outliving Design Patterns row has a verdict, or is set aside with why." Invoke the `brain` skill to record the **new** ones as drafts, each in the notes of the repository it bears on. For a spec of one milestone with few Notes, sift them inline instead. Done when the explorer's report holds a verdict for each source, re-dispatching it once when one is missing, and each **new** one sits in a draft, or nothing was left to keep.

4. **Clean up and hand over.** For each repository whose base is a release branch, offer the port by [RELEASE.md](RELEASE.md)'s **Port to the default branch**. In each repository, offer to delete the spec's branches (`git -C <root> branch -D` on each of `git -C <root> branch --list 'sdd/<spec-folder>/*'`, except `sdd/<spec-folder>/port`, which `/open-pr` opens): the spec's branch, since each squash already deleted its milestone's; delete them when the user agrees. Then release the build's claims by its **Locks**. Report every milestone, from its files: its repository, the tickets built with their **Commit** lines (each marked squashed, its commit on no branch now), what its `review.md` fixed, and its **Squash** and **Landed** commits. Then report one **Decided for you** section listing each escalated finding across the milestones' `review.md` files whose Answer the arbiter gave (every one not `decided by the user`), with its milestone and Answer, each `Needs the user:` bullet of the tickets' and milestones' Notes, and each draft step 3 left; then the commits now on each base, and that the spec is built. When any repository in **Repos** has a remote, add the hint `/open-pr <spec-id>` to open its PRs, one per landing, and `/open-pr <spec-id> --merged` once they merge, since a spec that depends on this one waits for that. For each repository whose card has an `explored` line, add the hint `/brain explore <slug>` once its base is pushed, so its explored notes catch up with the change. Done when the port and branch-deletion offers are answered, the claims are released and the user has the report.

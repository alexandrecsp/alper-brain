# Land the spec

A milestone **lands** when its squash reaches its repository's base, as one commit per milestone, with no merge commit. A track lands only while it is idle, by the build's **Tracks**, and only its **landable** milestones: a milestone is landable once it is squashed, every earlier milestone of its track is landed or landable, and every milestone its **Lands after** names has landed. Landing in that order gives each base the milestones in the order [CONTRACT-CHANGE.md](../../write-tickets/references/CONTRACT-CHANGE.md) cut them, so every base keeps working with the others.

Landing rebases a track's spec branch, so each squashed milestone's **Squash** line follows its commit through every rebase: right after one, each milestone's commit is the one in `git -C <root> log --format='%H %(trailers:key=Sdd-Milestone,valueonly,separator=%x2C) %s' <base>..sdd/<spec-folder>/spec` whose `Sdd-Milestone` trailer names it, by the build's step 10. A squash committed before that trailer existed has none: it is the one whose subject is its squash's. A milestone has **landed** once its **Squash** commit is on its base (`git -C <root> merge-base --is-ancestor <Squash SHA> <base>`); a fast-forward keeps the SHA, so its **Landed** commit is that same one.

## Land a track

Work in the track's repository by [FORMAT.md](../../brain/references/FORMAT.md)'s working repository rules, and find its base branch by the build's **Branches**. The landing takes the track's landable milestones; when it has none, there is nothing to land. When the call lands as it goes, the user's answer at the build's step 1 approves it; at the end, **When no milestone is open** asks first.

1. **Check what has landed.** A landable milestone whose **Squash** commit is already on the base landed in an earlier call that stopped after its merge: record those by step 3 first, as one landing, then land the rest by steps 2 and 3. Done when every landable milestone is listed as landed or still to land.

2. **Land them.** When `git -C <root> status --porcelain` is not empty, report it and stop. Run `git -C <root> rebase <base> sdd/<spec-folder>/spec`; on a conflict, run `git -C <root> rebase --abort`, report the conflicting files, tell the user that once they rebase `sdd/<spec-folder>/spec` onto `<base>` themselves, running the same `/build` again lands it, and stop. Then write each squashed milestone's rebased commit into its **Squash** line, as the paragraph above finds it; when a milestone's commit is missing, since the rebase dropped a squash already on the base, report the milestone and stop. The landing's **head** is its last milestone's **Squash** commit. Run `git -C <root> checkout --detach <head>`, then the repository's full suite.
   - When it fails and the head is the branch's tip, the base's new commits broke the spec: check out the spec's branch, dispatch a fixer by the build's step 9 fixer brief (the one opening "Make this failing check pass"), with the Context block (**Branch** `sdd/<spec-folder>/spec`), the paths of the last milestone's `milestone.md` and `spec.md`, and the failing command and the end of its output. Fold its commits into the last squash, so each milestone stays one commit (`git -C <root> reset --soft <head>`, then `git -C <root> commit --amend --no-edit`), write the amended commit into that milestone's **Squash** line as the new head, and run the suite again. After two failed fixes, write `failed` into the last milestone's **Phase** line, report the failure and stop, leaving the base untouched.
   - When it fails and the head is below the tip, check out the spec's branch, write `failed` into the last milestone's **Phase** line, report the failure and stop: a fix there would have to rewrite the squashes above it.

   With the suite passing, check out the base, run `git -C <root> merge --ff-only <head>`, and check out the spec's branch again. Done when the base holds the head, or the track stopped with the spec's branch checked out.

3. **Record it.** Append one entry for this landing to `spec.md`'s **Landings** line, in the form FORMAT.md's **Specs** gives it, creating the line under the **Base** line; skip an entry the line already ends with. Then set each landed milestone's **Landed** line to its **Squash** commit, replacing its `none`, and write `landed` into its **Phase** line. Done when the **Landings** line ends with this landing's entry and each landed milestone's **Landed** names its commit.

## When no milestone is open

1. **Land the rest.** When the call lands at the end, first ask the user once before changing any base, naming each repository and the milestones that land in it, in the order they will land; when they decline, stop. Then, until no track that has not stopped has a landable milestone left, land each such track by **Land a track**, in the order of the spec's **Repos** line, skipping a track once it has stopped: one track's landing can make another's landable. Done when every milestone's **Landed** names a commit, or the user declined, or a track stopped.

2. **Record the spec's landing.** Write `**Landed:** <slug>@<SHA>, …` into `spec.md`, under its **Base** line, with one entry per repository in **Repos**: the **Landed** SHA of its last milestone. Specs that depend on this one wait for that line. Skip this while any milestone is open or unlanded, or when `spec.md` already has its **Landed** line. Done when `spec.md` holds the **Landed** line, or a milestone has not landed.

3. **Clean up and hand over.** In each repository, offer to delete the spec's branches (`git -C <root> branch -D` on each of `git -C <root> branch --list 'sdd/<spec-folder>/*'`); delete them when the user agrees. Report every milestone, from its files: its repository, the tickets built with their **Commit** lines, what its `review.md` fixed, and its **Squash** and **Landed** commits. Then report one **Decided for you** section listing each escalated finding across the milestones' `review.md` files whose Answer the arbiter gave (every one not `decided by the user`), with its milestone and Answer, and each **Needs the user** item a sub-agent reported with the default it took; then the commits now on each base, and that the spec is built. When any repository in **Repos** has a remote, add the hint `/open-pr <spec-id>` to open its PRs, one per landing. For each repository whose card has an `explored` line, add the hint `/brain explore <slug>` once its base is pushed, so its explored notes catch up with the change. Done when the user has the report.

4. **Keep what was learned.** The tickets' Notes and the review answers live in the brain's `.sdd/`, on this machine only, so whatever they hold that a later change needs is lost with it. Dispatch one `alper-brain:scout`, its brief opening with the Context block by [BRIEF.md](../../brain/references/BRIEF.md) (**Works in** the brain, **Also reads** each repository in **Repos**, **Spec** the spec folder, never a ticket's path, **Docs** the absolute path of the `design-patterns` skill's `SKILL.md`, **Writes** nothing), with this brief: "Gather the gotchas from the tickets' Notes, the escalated Answers in the milestones' `review.md` whose reasons a later change would need, and the spec's Design Patterns rows that the **Recording** section of the `design-patterns` SKILL.md under **Docs** says outlive the spec. For each, find whether the code on its repository's base, an ADR, or a note under the brain's `repos/<slug>/` or `shared/` already states it, and report it as **stated**, with the file, or **new**, with the repository it bears on." The spec does not survive, so it is no reason to drop a candidate. Invoke the `brain` skill to record the **new** ones as drafts, each in the notes of the repository it bears on. For a spec of one milestone with few Notes, sift them inline instead. Done when each **new** one sits in a draft, or nothing was left to keep.

An **in-flight** spec, by [FORMAT.md](../brain/FORMAT.md), is drafted, ticketed, building, or built but not on its bases yet. Its code is missing or half-built, so its `spec.md` is the truth about what that code will be: its **planned state**. In-flight specs span every repository in the brain, so a spec in one repository can overlap work in another.

1. **Find the overlaps.** Dispatch one `alper-brain:scout` agent, its brief opening with the Context block by [BRIEF.md](../brain/BRIEF.md) (**Works in** the brain's `.sdd/specs/`, read only, **Writes** nothing), with the modules the topic touches, each with its repository's slug; the interfaces between repositories the topic changes, with the `contract` notes the work's recall found; the in-flight spec folders' paths; and this brief: "For each spec folder, list the modules it builds or changes, each with its repository: from its `spec.md`'s Implementation Decisions and the Where of its Design Patterns rows, or, when its `spec.md` has no Implementation Decisions, from its milestones' **Shape** and its tickets' **What to build**. A module's repository is the module-map `subgraph` it sits in, else the track folder its milestone sits in (`milestones/<slug>/`, or the milestone's **Repo** line in a spec whose milestones sit straight under `milestones/`), else the spec's one **Repos** slug. Report the spec as **overlapping** when it builds or changes a module the topic touches in the same repository, or changes one of the interfaces or contracts given, naming each shared module or interface. Match modules by the code unit they name, whatever the label's wording, and report a match you are unsure of as **possible**, with the reason. For each overlapping spec, state what it leaves each shared module or interface as: its `spec.md`, overridden by the Notes of its `done` tickets wherever they disagree." Done when every in-flight spec is reported as overlapping (each shared module or interface with its planned state), possible, or not.

2. **Read the planned state** of each overlapping spec from the scout's report; open its `spec.md` yourself only where the report leaves a shared module or interface unclear. Settle each **possible** overlap with the user. Done when you can state, per shared module or contract, what each overlapping spec leaves it as.

3. **Report** to the user which specs the work builds on, and the modules or contracts each shares. Design against their planned state, never the code those modules hold now.

An in-flight spec stays as written. When the work needs one to change (a different interface at a shared seam, a renamed term), ask the user whether to design around it or to revise that spec separately. When the user says an overlapping spec will never be built, write `**Abandoned:** <the user's reason>` into its `spec.md`, under its **Key** line, and drop it from the overlaps.

A **contract change** changes an interface one repository offers another: an API, an event, a queue or a shared schema, with a **producer** that offers it and **consumers** that call it. Each repository lands on its own base and deploys on its own schedule, so no moment exists when every side switches at once. Sequence it as **expand–contract across repositories**, in milestones that each leave every repository working with every other one as it stands:

1. **Expand**, in the producer: offer the new shape beside the old one (a new field the old consumers ignore, a `v2` route or event next to `v1`), so every consumer keeps working.
2. **Migrate**, one milestone per consumer: move it onto the new shape. The old shape still exists, so each consumer lands and deploys alone. Its **Done when** proves the consumer against the new shape at the consumer's own seam (a contract test, or the producer stubbed, by [CONTRACTS.md](../tdd/CONTRACTS.md)), since the producer's expand is landed only on this machine, unpushed and undeployed.
3. **Contract**, in the producer, after every migrate milestone: remove the old shape. `build` lands it on the producer's base right after the last migrate, before anyone has deployed a consumer, so it is safe to deploy only after every consumer's migrate is deployed. Ask the user in the quiz whether to keep it in this spec (they then deploy the producer's base after every consumer) or to leave it for a follow-up spec, and record the answer in the spec's Further Notes.

The milestone order is the order the repositories land in: the producer's expand, then the consumers, side by side in one wave, then the producer's contract. Hold that order with **Depends on**: each migrate's first ticket names the expand's last ticket, and the contract's first ticket names the last ticket of every migrate. A consumer's migrate can share a milestone with that consumer's other work in the spec, and the expand with the producer's work before it; the expand and the contract never share one.

A change every consumer already tolerates, such as an optional field added, needs only its producer milestone. When the user keeps the old shape (for consumers outside the brain, or until the consumers deploy), leave the contract step out and record why in the spec's Further Notes.

## Consumer check

Whether a change to a contract still serves its consumers is read from the consumers' code, never guessed from the producer's. For each `contract` note whose interface the change touches, dispatch one `alper-brain:scout` per consumer its `repos` names other than the producer and that is linked, all in one message, each brief opening with the Context block by [BRIEF.md](../brain/BRIEF.md) (**Works in** the consumer, read only, **Notes** the contract note, **Writes** nothing), then the change (the hunks that change the interface, or the spec's decision that changes it) and this brief:

> List every place this repository calls or reads the interface the contract note records, on its base branch (read it with `git -C <root> show <base>:<path>`; the working tree may hold another branch), each with its `path:line`. For each, say whether it still works with the changed shape: **works**, **breaks** (how), or **unknown** (what would tell). Then say whether this repository tolerates the change as it stands, or must move onto the new shape. Done when every call site has a verdict, or you report that there are none, with the searches you ran.

A consumer that is not linked is **unchecked**, with `/brain link` as the way to check it, and its explored notes as the only evidence. Each **breaks** stops the change from landing on its own: the consumer moves in a migrate milestone first, or the old shape stays offered.

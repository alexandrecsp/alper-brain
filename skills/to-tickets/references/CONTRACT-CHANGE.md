A **contract change** changes an interface one repository offers another: an API, an event, a queue or a shared schema, with a **producer** that offers it and **consumers** that call it. Each repository lands on its own base and deploys on its own schedule, so no moment exists when every side switches at once. Sequence it as **expand–contract across repositories**, in milestones that each leave every repository working with every other one as it stands:

1. **Expand**, in the producer: offer the new shape beside the old one (a new field the old consumers ignore, a `v2` route or event next to `v1`), so every consumer keeps working.
2. **Migrate**, one milestone per consumer: move it onto the new shape. The old shape still exists, so each consumer lands and deploys alone. It builds beside the expand, against the shape the spec pins, so its **Done when** proves the consumer against the new shape at the consumer's own seam (a contract test, or the producer stubbed, by [CONTRACTS.md](../../tdd/references/CONTRACTS.md)): the producer's expand is unpushed and undeployed, and may still be unbuilt when the migrate builds; `build` then checks the migrate's fakes against the expand's code by [MIGRATE-CHECK.md](../../build/references/MIGRATE-CHECK.md), so pin the shape precisely.
3. **Contract**, in the producer, after every migrate milestone: remove the old shape. `build` lands it on the producer's base right after the last migrate, before anyone has deployed a consumer, so it is safe to deploy only after every consumer's migrate is deployed. The user chooses in the quiz between keeping it in this spec (they then deploy the producer's base after every consumer) and leaving it for a follow-up spec; record the choice in the spec's Further Notes.

The repositories land in this order: the producer's expand, then the consumers, then the producer's contract. The expand and the contract are milestones of the producer's track, the migrates of each consumer's. Hold the order with each milestone's **Lands after** line, which orders the landing without holding the builds apart, so the migrates build beside the expand: each migrate lands after the expand, written `<producer>/NNN`, and the contract after every migrate, written `<consumer>/NNN`. A consumer's migrate can share a milestone with that consumer's other work in the spec, and the expand with the producer's work before it; the expand and the contract never share one.

The migrates build against the shape the spec pins under its API contracts, in the form [SPEC-TEMPLATE.md](../../to-spec/references/SPEC-TEMPLATE.md) asks. When the spec leaves a changed shape unpinned, ask the user in the quiz to pin it, and write the answer into that API contracts entry of `spec.md`. When the user cannot pin it before the expand is built, give each migrate's first ticket a **Depends on** the expand's last ticket, so the migrate builds after the expand squashes and takes the shape from the expand's code, and say why in the quiz.

A change every consumer already tolerates, such as an optional field added, needs only its producer milestone. When the user keeps the old shape (for consumers outside the brain, or until the consumers deploy), leave the contract step out and record why in the spec's Further Notes.

## Consumer check

Whether a change to a contract still serves its consumers is read from the consumers' code. For each `contract` note whose interface the change touches, dispatch one `alper-brain:scout` per consumer its `repos` names other than the producer and that is linked, in waves by BRIEF.md's **Fanning out**, each brief opening with the Context block by [BRIEF.md](../../brain/references/BRIEF.md) (**Works in** the consumer, read only, **Notes** the contract note, **Branch** the consumer's base branch, which you resolve first: its entry in the spec's **Base** line, else its remote's default, **Writes** nothing), then the change (the hunks that change the interface, or the spec's decision that changes it) and this brief:

> List every place this repository calls or reads the interface the contract note records, on its base branch (read it with `git -C <root> show <base>:<path>`; the working tree may hold another branch), each with its `path:line`. For each, say whether it still works with the changed shape: **works**, **breaks** (how), or **unknown** (what would tell). Then say whether this repository tolerates the change as it stands, or must move onto the new shape. Done when every call site has a verdict and you have said whether this repository tolerates the change or must move, or you report that there are no call sites, with the searches you ran.

A consumer that is not linked is **unchecked**, with `/brain link` as the way to check it, and its explored notes as the only evidence. Each **breaks** stops the change from landing on its own: the consumer moves in a migrate milestone first, or the old shape stays offered. Done when every linked consumer's report has a verdict for every call site and its tolerates-or-moves answer, re-dispatching a scout whose report leaves one out, and every unlinked consumer is listed as unchecked.
